# Supabase Schema Audit — GFC Inventory System

> Generated by cross-referencing the **repo-reconstructed effective schema** (86 SQL files layered in order)
> against **actual application usage** (`app/` + `lib/`: every `.from()`, `.rpc()`, `storage.from()`,
> `.select()`, `.insert()`, `.update()`, filter chain, and the TypeScript row types in `lib/supabase.ts`).

## ✅ VERIFIED against a live dump

This audit has been **reconciled against a live `information_schema` dump** taken from the production
Supabase project (raw CSVs in `schema/dumps/`: `columns.csv`, `row_counts.csv`, `views.csv`,
`constraints.csv`, `indexes.csv`, `functions.csv`, `policies.csv`). Live snapshot: **80 public tables**,
**3 views**, **1015 columns**, **22 functions**, **81 RLS policies**.

The live dump **overturned several earlier (repo-only) assumptions** — most importantly, some columns/tables
the app references do **not** exist in production either, meaning those code paths are **actively broken**, not
dashboard-created. Those are now reclassified as 🐞 **BUG** below.

## Classification legend

| Status | Meaning |
|--------|---------|
| ✅ **USED** | Defined in repo SQL **and** referenced by the app. |
| 🟡 **AMBIGUOUS** | Table is used, but only via `select('*')`, so individual unused columns can't be proven from queries alone. |
| 🟠 **UNUSED** | Defined in repo SQL, but **no** `.from()` reference in the app. Candidate for removal (verify row count + triggers first). |
| 🔴 **MISSING-OK** | Absent from repo SQL but **present in live DB** (created via dashboard). Works in prod; add to canonical so fresh installs match. |
| 🐞 **BUG** | Referenced by app code but **absent from BOTH repo SQL and the live DB** → that feature is currently broken in production. |
| ⚫ **DROPPED** | Created by one migration and dropped by a later one — confirmed **absent** from live DB. |

## Headline summary (live-verified)

- **80 public tables** + **3 views** (`inventory_summary`, `materials_stock_view`, `po_summary_view`) + **22 functions** in production.
- **Table-level usage (verified by script):** of the 80 live tables, **76 are referenced by `.from()`**, `admin_credentials` is used **via RPC only**, and **3 are genuinely unused** (`quotations`, `quotation_items`, `material_stock_alerts`).
- **Column-level usage (verified by script):** only **3 live columns never appear anywhere in app code** — `daily_stock_summaries.total_released`, `production_schedules.allow_override`, `staff_schedules.hours_manual_override`. All other 1000+ columns are referenced at least textually.
- **`announcements` EXISTS in live** (7 rows) — dashboard-created, not in repo SQL. 🔴 MISSING-OK.
- **All 🐞 BUG items have been RESOLVED** (see the BUG section below for the fix applied to each).
- **Confirmed-present dashboard columns:** `staff_registrations.hourly_rate`/`employment_date`, `locations.can_access_order_features`, `staff_schedules.hours_manual_override`.
- **UNUSED + empty (safe to drop after FK/trigger handling):** `quotations` (0), `quotation_items` (0), `material_stock_alerts` (0).
- **`gfc_product_retail_mapping`** — confirmed **absent** (retail-direct migration applied cleanly). ✅
- **`gfc_material_legacy_mapping`** — also **absent** from live; not referenced by app → no action needed.
- **`daily_inventory`** — no table (TS type only).
- **Storage bucket bug** stands: deposit slips use two names (`deposit-slips` vs `deposit_slips`).
- **Fleet GPS** — 5 tables + 2 functions + 1 trigger now in `canonical-schema.sql` (Section 4b). Migrations archived under `schema/migrations/_archive/`.
- **Incremental migrations** — `schema/migrations/` now holds only active one-off upgrades; consolidated DDL lives in `canonical-schema.sql`. See `schema/migrations/README.md`.
- **Extra live functions** not in repo migrations (made in dashboard): `generate_grn_number`, `generate_po_number`, `generate_pr_number`, `set_po_number`, `log_purchase_order_changes`, `log_purchase_order_changes_v2`, `update_dsir_calculations`, `update_po_total`. Review whether these are still wired to triggers.

## 🐞 BUG — app referenced objects absent from live DB (✅ ALL RESOLVED)

These code paths used to throw at runtime (querying/writing a column or table Postgres didn't have). Each has
now been fixed — either by aligning the app code to the live shape, removing dead logic, or creating the one
table that backs a real feature.

| Object | App code | Resolution |
|--------|----------|------------|
| `dsir_expenses.particulars` | `DSIRForm.tsx`, `DSIRSections.tsx` | ✅ **Code fixed** — renamed `particulars` → `description` (the live column, also read by `DSIRViewer.tsx`). |
| `staff_schedules.is_rest_day` | `StaffSchedule.tsx` | ✅ **Code fixed** — references removed; the value was always `false` (vestigial logic) and the `.eq('is_rest_day', false)` query was crashing the schedule load. |

| `fixed_asset_movements` (table) | `FixedAssetsPanel.tsx` (mounted), `accounting-procurement-posting.ts` | ✅ **Table created on live** — real, active feature. Added table + `update_fixed_asset_quantity` trigger + index + RLS (`schema/dumps/apply-fixed-asset-movements.sql`). Verified present. |

## Notable mismatches & cleanups (review needed)

1. **`staff_assignments` has two shapes.** Legacy/main flow uses `staff_registration_id`; `StaffCodeManager`
   uses `staff_code_id` + `brand_id`. Confirm the live table and decide whether to consolidate.
2. **`dsir_expenses.particulars` vs `expense_type`.** App write path (`DSIRForm`/`DSIRSections`) uses
   `particulars`; read path (`DSIRViewer`) uses `expense_type`. One of them is wrong against the live schema.
3. **Deposit-slip storage bucket name split:** `app/order/page.tsx` uses `deposit-slips`; `OrderManager.tsx`
   uses `deposit_slips`. Pick one and migrate.
4. **Duplicate DSIR definitions:** `complete-schema.sql` and `dsir-schema.sql` both define the `dsir_*` tables
   with **different columns** (e.g. `dsir_ice_cream_inventory.flavor` is `VARCHAR(100)` vs `VARCHAR(50)`, and the
   dsir-schema variant adds `new_inventory`/`sold`/`price`/`sales`). Because both use `CREATE TABLE IF NOT EXISTS`,
   whichever ran first wins. The canonical file standardizes on the `complete-schema.sql` shape **plus** the
   columns the app actually reads.
5. **Two markup-percent columns** coexist on `accounting_voucher_settings`:
   `default_intercompany_markup_percent` (added by factory-rollout) and `intercompany_default_markup_percent`
   (added by retail-direct, `NOT NULL`). The app reads `intercompany_default_markup_percent`. The other is
   redundant — review for removal.
6. **`add_production_details_column.sql`, `customer-orders-shipment-delivery-type.sql`,
   `dashboard-guest-passcode.sql`** are effectively no-ops (redundant or comment-only).

## Per-field deep trace (select('*') tables)

Because most reads use `select('*')`, the column-name sweep can't tell "fetched-but-ignored" from "actually
consumed". These three high-value tables were traced field-by-field (every column checked for real reads,
inserts, updates, and render/print usage — references that exist **only** in the `lib/supabase.ts` type were
treated as dead).

| Table | Columns | Genuinely consumed | Fetched-but-never-used (type-only) |
|-------|---------|--------------------|-------------------------------------|
| `purchase_orders` | 29 | 27 | **`quotation_id`**, **`actual_delivery_date`** — appear only in the TS type, never read/written. `quotation_id` matches the dormant `quotations` feature. |
| `accounting_vouchers` | 47 | **47 (all)** | none — every field is used in the voucher form, `accounting-voucher-service.ts` insert, and/or print templates. Low textual counts were just a wide table. |
| `staff_registrations` | 11 | **11 (all)** | none. |

Notes:
- `purchase_orders.paid_amount` / `balance_amount` are written as `0` by the app and then maintained by the
  `update_po_balance` trigger; they're consumed via `po_summary_view`. Counted as used (server-maintained).
- The two dead PO columns are low-risk to drop but harmless to leave; left in `canonical-schema.sql` to match live.
